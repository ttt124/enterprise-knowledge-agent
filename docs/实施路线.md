# 第3题实施路线：企业知识问答 Agent

状态更新：2026-11-07，核心实现和验证已完成。以下保留最初的实施设计与准备过程，包含当时未实现或尚未配置的历史描述；当前运行方式、标准库依赖取舍和实际结果以根目录 README.md、docs/02-solution.md、docs/03-evaluation.md 为准。用户已在本机配置API，最终真实模型九例通过本项目断言。本人提供的投入时长估算为约3小时，个人学习确认仍需本人完成。

## 1. 最终要做成什么

员工在命令行提问，模型选择检索与原文读取工具，根据返回结果决定继续查证、回答、追问或停止。每次输出包含回答、文档 ID 与逐字原文、资料缺口和任务状态；同时留下可核查 Trace。

建议先完成一个原生 Python 工具调用循环。使用本地 JSON 合成资料；检索可以采用关键词、同义词与主题召回。小型语料可以返回同一主题的全部候选，避免过小的 top-k 隐藏冲突，但要如实说明扩展性和召回边界。是否能处理改写问题必须实测。

## 2. 第一步：准备并检查模型 API

建议先使用 DeepSeek 官方 API。2026-11-07 查阅官方文档时，示例模型名为 `deepseek-flash`，兼容地址为 `https://api.deepseek.com`；工具调用文档提供 Python 非思考模式示例。模型名与账户可用性以实际控制台和当时官方文档为准。

1. 打开 https://platform.deepseek.com/ ，完成自己的账户注册与 API Key 创建。
2. 查看控制台额度和价格；需要充值时，由本人在控制台决定。
3. 在项目内创建虚拟环境，安装依赖；复制 `.env.example` 为 `.env`。
4. 只在本机 `.env` 中填写 `LLM_API_KEY`，保留模型及地址配置。
5. 执行 `scripts/check_model.py`。检查必须同时看到：模型请求工具、本地执行工具、工具结果回传模型、最终回答包含工具返回的随机校验码。

PowerShell 命令见 README。连通性检查不构成正式项目验收，也不能替代两条不同的模型决策路径。

官方依据：

- https://api-docs.deepseek.com/zh-cn/
- https://api-docs.deepseek.com/zh-cn/guides/tool_calls/

## 3. 第二步：准备一小份可验证的资料

先准备 6—8 条短小合成制度，写入计划文件 `data/documents.json`。每条至少包含 `doc_id`、`title`、`version_date`、`content`；可增加 `topic`、`keywords`、`scope`，未知适用范围明确写 null。

用自拟的合成业务事实组织资料，避免上传试卷原文。建议包含：

- 一个只有单一依据的制度事项，用来验证明确回答。
- 一个出现两种不同规定的事项，且资料没有提供优先级或适用范围，用来验证冲突。
- 与上述事项相关、但没有写出冲突裁决关系的说明，用来验证补查后仍需确认。
- 另一主题的制度，用来区分上下文指代。
- 至少一个资料库完全不涵盖的问题。

设计冲突资料时，不能因为其中一份日期较新，就默认它覆盖另一份；除非资料明确给出效力关系。

## 4. 第三步：实现两个业务工具

以下均是计划接口，文件与函数尚未实现。

| 工具 | 输入 | 输出 | 验证重点 |
| --- | --- | --- | --- |
| `search_documents` | 查询词，必要时包含主题 | 候选 ID、标题、日期、相关摘要 | 改写问题能召回；同一主题的冲突候选不被静默过滤 |
| `read_document` | 文档 ID | 当前原文、片段 ID、日期 | 引用确实来自本次读取的原文 |

搜索不到返回明确的空结果；工具异常返回明确错误类型，二者不能混同。故障注入由测试输入控制，不交给模型自行宣称工具失败。

## 5. 第四步：完成真正的模型决策循环

```text
问题 + 可选对话历史
  → 模型决定工具与参数，或决定结束
  → 程序校验参数并执行工具
  → 把真实工具结果追加到消息历史
  → 模型观察结果，再决定下一步
  → 回答 / 追问 / 说明资料不足 / 明确未完成
```

程序负责工具白名单、参数校验、执行上限、Trace、引用校验。模型负责选择动作、补查方向、是否追问或结束。引用校验属于程序约束，不应在校验失败后自行编出答案。

建议设置最大工具调用次数，例如 8 次，失败调用也计数。达到上限且仍未完成时返回 `incomplete`，明确原因，不再执行工具。需要严格定义计数与结束行为。

历史消息只帮助还原“那期限呢”等指代，不作为制度事实。回答仍须检索、读取当前资料；指代存在歧义时追问。

建议结构化结果：

```json
{
  "answer": "基于本次查得资料给出的答案或冲突说明",
  "citations": [
    {"doc_id": "SYN-001", "version_date": "2026-10-01", "quote": "从原文逐字摘录的证据"}
  ],
  "gaps": [],
  "status": "completed",
  "reason": "证据充足"
}
```

状态建议：`completed`（证据充足）、`needs_clarification`（缺用户确认或冲突无法消解）、`insufficient_evidence`（资料不覆盖）、`incomplete`（工具持续失败或达到上限）。具体命名可调整，但必须清楚区分成功与未完成。

Trace 记录步骤、模型选择的工具、参数、返回摘要、后续动作与简要依据。依据只记录面向用户的简短说明，例如“已发现冲突，补查适用范围”；不要求记录模型内部思维过程。可执行步骤与工具结果必须来自真实运行，不手工预写。

## 6. 第五步：按验收矩阵跑实际记录

| 用例 | 输入或变化 | 应观察到的行为 |
| --- | --- | --- |
| T01 明确答案 | 询问单一制度事实 | 检索、读取、回答；引用逐字匹配且支持结论 |
| T02 文档冲突 | 同事项存在不同规定，无优先级 | 读取双方，补查；仍无裁决依据则披露冲突并请求确认 |
| T03 资料外问题 | 问资料库不覆盖的问题 | 根据空结果决定改写查询或停止/追问；不凭常识编制度 |
| T04 改写问题 | 将 T01 换为口语或同义表达 | 找到同一依据，事实和引用一致 |
| T05 上下文追问 | 首问明确对象，次问“那期限呢” | 利用历史还原对象，依据当前文档回答；歧义时追问 |
| T06 工具失败 | 注入检索或读取持续失败 | 工具实际报错；模型据此调整或停止，不能伪装成功 |
| T07 执行上限 | 测试中让模型持续请求工具 | 按定义停止并返回未完成；可由可控测试模型稳定验证，须标注其范围 |
| T08 原文替换 | 修改 T01 资料中的事实值，重新运行 | 回答与引用随当前原文变化，无旧缓存或硬编码 |
| T09 新增冲突 | 在 T01 语料中加入冲突文档，重新运行 | 从直接回答转为查证、披露冲突与追问 |

T01—T06覆盖所选题六项必验场景；T07验证统一执行上限；T08—T09对应评审会更换文档的检查。至少三组实际输入、输出和运行记录覆盖正常、资料不足、工具失败；直接保存全部用例更便于评审核查。

正式真实模型路径至少保存两条：

1. 检索得到可靠候选 → 读取原文 → 证据充分后回答。
2. 同问题检索到冲突候选 → 读取双方 → 补查仍不足 → 披露冲突并追问。

另保留一条工具实际失败后模型调整动作或停止的记录。离线 Mock 用例、单元测试与真实模型记录分别标明，不能用 Mock 通过数冒充模型效果。
