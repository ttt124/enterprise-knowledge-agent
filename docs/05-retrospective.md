# 项目复盘

## 当前可以支持的结论

本项目以本地小型知识库构建企业知识问答 Agent 演示，保留模型工具选择与证据回传过程，让评审者能够检查答案如何产生。Python 3.13.14 环境下，最终 `deepseek-flash` 实时用例业务与证据断言通过 9/9，28 项单元测试通过；离线模拟流程断言通过 9/9，业务效果不评估。这是固定测试集的结果，不是通用正确率或生产能力证明。

## 方案取舍

初始环境准备中遇到 SDK 安装下载较慢的问题，因此改用 Python 标准库 `urllib` 实现 HTTP 调用，降低第三方安装依赖。代价是需要自行处理请求结构、响应解析和接口错误；没有实际覆盖的异常不能据此宣称已解决。

采用关键词、同义词及中文双字片段检索，优点是六份短资料下可解释、容易核验。同主题候选一并召回，有助于暴露刻意设置的制度冲突。其局限是语义泛化、长文定位和规模扩展能力需要额外评估，不宜据此推断企业级检索效果。

将模拟与实时运行分开，可以在 API 不可用时检查工具流程，并避免将预设模拟答案误当作真实模型能力。测试流程可运行不等于问答效果合格，二者应分别报告。

## 关键认识

第一次实时评测的自动检查曾通过 9/9，人工检查却发现两项错误：T02 在未确定制度优先级时建议先按较严格的 15 天执行；T06 在读取持续失败时转述检索摘要中的 7 天。前者越过证据作出执行建议，后者把未读取的摘要当作事实。修复时加强提示，增加禁选建议和未读数字断言后重新评测，最终通过；旧输出及 [posthoc-review.json](../examples/live/run-20261107T130612599867Z/posthoc-review.json)保留，复核记录将旧 T02、T06 判为失败。

代码审查还发现：工具预算恰好用完时，程序提前停止，未给模型使用最后一次结果收尾的机会；默认 HTTP 重定向可能转发鉴权头。前者已改为预算用满后允许一次无工具收尾，后者已改为拒绝重定向，并通过假密钥本地 302 测试。两项均纳入回归检查。

- 能给出看似合理的答案不足以完成知识问答：还要核验资料来源、是否遗漏冲突，以及是否在证据不足时停止推断。
- 引用逐字匹配是可自动检查的底线，仍需人工检查引用是否支持结论。
- 错误处理不应只处理网络失败，也应覆盖未知工具、参数错误、资料不足、工具次数耗尽和模型轮数耗尽。
- 变更事实和新增冲突后的复测，比只检查一份固定答案更能揭示硬编码或遗漏证据的问题。

## 尚存边界与后续工作

最终实时评测及主要路径人工核对已经完成，但提示与正则断言不是通用语义证明；其他措辞、复杂追问、大规模语料和服务变化仍可能产生失败。当前不具备生产部署、实际业务使用或量化收益证据，不报告吞吐、准确率提升、节省人力或线上稳定性等指标。

后续优先依据实际失败样本修正提示与检索策略，再考虑资料版本、访问权限、复杂文档处理和更大规模检索。每项扩展都需要单独验收，不视为当前能力。

用户仍需亲自运行、阅读并解释程序，才能将本项目转化为自己的可陈述经验。当前没有可靠的个人工时记录或独立开发证据，不编造个人实施过程。
