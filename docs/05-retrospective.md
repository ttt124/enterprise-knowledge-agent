# 项目复盘

## 项目结果

本次提交保留了模型动作、工具执行、证据返回和最终回答之间的完整链路。在 Python 3.13.14 环境下，28项自动化测试通过，`deepseek-flash` 的9个真实模型用例通过本仓库断言；离线模式另行记录流程检查结果。具体记录见[评估文档](03-evaluation.md)。

## 主要技术取舍

项目采用标准库HTTP客户端和本地JSON资料库。SDK下载缓慢促使实现转向标准库，减少安装依赖，便于直接复现；相应代价是需要在项目内处理请求协议、超时、错误和重定向。

关键词、同义词和中文双字片段检索适合本次小规模短文档。同主题候选一起返回，可以保留冲突来源；随着资料增加，也可能产生弱相关召回或语义漏检，需要再评估排序与召回策略。

模型负责选择动作，本地程序负责参数校验、执行预算和引用检查。这样既保留动态决策，也能明确限制工具执行次数，避免模型将搜索线索直接当作已核验原文。

## 最难的问题：检查通过不等于证据充分

首次真实评估的自动检查为9/9，但进一步复核暴露了两项缺陷：

- 冲突回答同时列出了两个期限，却附加“先按较严格期限执行”的建议，仍然越过了资料依据。
- 原文读取失败后，回答转述了搜索摘要中的期限，容易让未核实线索看起来像确定结论。

修正方式是同时收紧提示和断言：冲突未消解时只说明双方依据并请求确认；关键原文读取失败时只报告故障与缺口。旧输出和[事后复核](../examples/live/run-20261107T130612599867Z/posthoc-review.json)保留，用于对照修正效果。这些分析与修订借助AI完成，协作范围见[AI使用说明](04-ai-usage.md)。

另两项边界问题也进入回归检查：工具预算恰好用满后，允许模型使用已有证据进行一次无工具收尾；HTTP客户端拒绝重定向，并通过本机假密钥测试核验302响应不会被继续访问。

## 收获与限制

这次交付体现出三个需要同时检查的层面：答案是否有来源、引用是否真正支持结论、后续动作是否随着工具结果变化。最终答案正确而Trace缺少实际工具调用，或引用逐字匹配但结论越过适用范围，都不能视为充分验证。

固定样例便于回归，但不能等同于通用准确率。当前仅覆盖六份短小合成制度、少量追问和故障场景，尚未验证长文、复杂歧义、权限隔离或大规模检索；没有生产部署与业务收益数据。
